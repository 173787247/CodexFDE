# 交互 2｜把风险写成长期规则

继续处理交互 1 的同一个案例。先读取：

- `AGENTS.md`；
- 当前目录下更具体的 `AGENTS.md`（若存在）；
- `docs/courses/tasks/L02-AGENTS项目约束.md`；
- 我在交互 1 后确认的规则归属与取舍。

目标：只补齐跨会话长期有效的项目规则，让后续 Codex 会话既不会绕过 FlowERP 底线，也不会误伤合法开发。

规则补丁至少应覆盖：

1. 项目主线与 `flowerp/`、`workbench/`、`eval/`、`web/` 的责任边界；
2. 不可破坏的长期业务不变量：库存非负、入库幂等、订单合法迁移与取消释放、采购审批后才能入库；
3. 禁止直接修改运行数据库、删除失败证据或把失败伪装成成功；
4. 证据优先级与统一验证入口；
5. Definition of Done：相关正反路径、阻断 Eval、修改摘要、剩余风险；
6. 每条高风险禁令对应的合法替代路径；
7. 文字规则不能替代真实权限、状态机、事务与审计。

约束：

- 不把 20、8、12、100 等本次动态数字写成长期事实；
- 不复制大段通用口号，不写无法验证的“确保高质量”；
- 不修改 `flowerp/`、业务数据库、测试结果或历史失败记录；
- 若现有规则已经覆盖某项，只做最小补丁并避免重复；
- 遇到根规则与就近规则冲突时，列出冲突并停止，不自行放宽上层底线。

执行顺序：

1. 先给出拟修改位置、五段式规则草案和预计 Diff；
2. 等我确认后再修改；
3. 修改后展示实际 Diff；
4. 运行 `python -X utf8 -m workbench.cli course-contract --lesson 2`；
5. 若环境允许，再运行 `python -X utf8 -m eval.harness --suite blocking`；
6. 报告命令、退出码、未完成项和剩余风险。

完成后停下，不要开始 FlowERP 功能开发。
