# L01｜以终为始：一次可验证的 AI 交付怎样完成？

**本卡主线：明确交付成果 → 解释工作台的必要性 → 说明协作与质量机制 → 设计个人工作台 → 用 V0.1 验证设计。**

先读 [学生讲义](./阅读讲义.md)第 1～4 节。完整命令、预期结果、记录方法与排错见[实践操作手册](./实践操作手册.md)，本卡用于实践时核对顺序。学习重点是解释设计选择及其验证依据；操作所需概念在手册中随步骤说明。

- **核心内容**：开课时没有个人工作台、`WORKBENCH_SPEC.md` 或验收测试；学生从一句模糊诉求和真实痛点出发，利用 Codex 完成需求访谈，由学生决定范围并签署首份 Spec，再把验收项转成红灯测试，开发初始化、项目登记、任务账、命令证据账和状态检查。
- **演示结果**：`“帮我搭建个人 AI 研发工作台”` 经历“原始诉求 → Codex 追问 → 学生取舍 → `WORKBENCH_SPEC.md` → 验收测试红灯 → Codex 实现 → 同一测试绿灯”，最后由新工作台记录自己的建设证据。
- **课内增量**：学生亲手形成并签署首份 `WORKBENCH_SPEC.md`、从验收项生成失败测试、开发出可运行的 Workbench V0.1，并完成第一次自举记录；本讲不接入、不开发 FlowERP。
- **通过标准**：Spec 每项关键要求能回指原始痛点、Codex 建议和学生决定；测试能回指验收项；必须保留实现前红灯、范围内 Diff 和实现后绿灯；学生能用自己开发的命令完成自举，并说明 L04 才会通过“个人工作台 + Codex”开发 FlowERP。

## 本讲目标卡

| 要完成的学习 | 对应产物 | 验收问题 |
|---|---|---|
| 解释为什么需要工作台 | `01-problem.md` | 两个具体问题、后果与拟解决能力是否对应？ |
| 解释怎样协同 Codex 提升质量 | `02-design.md` 中的角色与机制设计 | 谁决定、谁执行、谁验证？每项机制能拦什么、会漏什么？ |
| 设计自己的工作台 | 个人设计、决定表、签署的 Spec | 工作流能否推导对象、边界、失败行为和最小范围？ |
| 验证第一版设计 | 红灯、源码、Diff、后绿、自举记录 | 任务与证据能否关联？缺失是否如实报告？ |
| 解释并迁移 | 修订、第二次签字、迁移方案 | 能否区分已验证能力与目标设计，并适应另一个项目？ |

## 建设关系与本讲边界

- **Codex 角色**：学生直接监督 Codex 进行设计审查、需求访谈和实现；范围与验收由学生决定。
- **ERP 产品状态**：FlowERP 未接入，`flowerp_connected = false`，本讲不开发库存导出。
- **工作台增量**：V0.1 的初始化、项目登记、任务记录、命令证据与状态检查。
- **因果关系**：持续 ERP 交付需要稳定的要求、任务身份和验证记录，因此先验证任务与证据账的设计；L04 再接入执行并交付库存导出。
- **学习证据**：三问答案、首次判断、个人设计、Spec 取舍、有效红灯、实际 Diff、同标准绿灯、失败后状态、反馈与修订。

V0.1 不自动调用 Codex；完整目标设计中的受控执行、统一复验与审核连接尚待后续实现。状态完整不能单独证明交付质量提高。

## 起点与环境

先完成 [L00](../tasks/L00-课前准备.md)。按实践手册选择 Windows 或 macOS/Linux 命令，使用参考仓库的虚拟环境。

在参考仓库根目录运行实践手册第 1 节 的隔离准备块：`course-prepare --lesson 1 --source working-tree`，使用新的 `TASK-L01-` 编号。该入口将当前源码复制为本地独立快照并剥离 L01 能力，能包含尚未提交的课程源文件。

核对返回的 `path`、`baseline_semantics = working_tree_snapshot` 与 `student_start.start_gap_applied = true`。这是本地教学快照，不是已发布课程标签；其中不包含二进制 PPT。不能据此声称正式课程基线发布或学生已达成。

进入隔离区后必须检查：Spec 不存在、L01 测试不存在、目标命令不可用、导入模块来自隔离目录。其他课程骨架仍可存在，不能把整个仓库描述为没有参考代码的空目录。

在 VS Code 和 Codex 当前任务中使用同一隔离目录。重开终端后的恢复见实践手册第 7 节。不要删除旧练习与失败记录来重新开始。

## 命令与证据速查

| 命令 | 必须核对的结果 |
|---|---|
| `workbench-init` | 所有者、工作台 ID、V0.1、运行位置 |
| `workbench-project-add` | `PERSONAL-WORKBENCH` 与当前隔离路径 |
| `workbench-task-create` | `CASE-WB-L01-001`、创建人、Spec 与问题快照 |
| `workbench-evidence-add` | 三条原始观察成功追加；红灯内部的非零退出码保留 |
| `workbench-status --require-red-green-evidence` | 缺记录时失败，齐全时 `pending_human_review` |

命令都通过 `python -X utf8 -m workbench.cli` 调用，完整参数见实践手册第 5 节。不要只复制此表中的子命令直接执行。

红灯、Diff、后绿每次使用独立时间目录，保存 `output.txt` 与 `meta.json`。前红和后绿必须是相同验收命令，观察时间严格递增，且实际测试标准没有被放宽。导入记录不会执行 `command-text` 中的命令，也不会认证观察者和原始时间。

`git status --short` 用于发现新增与范围外文件；`git add -N` 让本次新建测试进入 Diff，只在隔离区登记意图，不提交内容。若再次修改实现，重新采集 Diff 与后绿，保留旧记录。

## 验收卡

1. 学生能用自己的话完整回答三问；设计说明每项能力为何存在。
2. 关键需求能回指问题来源、Codex 建议和学生决定；测试能回指验收项。
3. 有效起点、实现前红灯、范围内 Diff 与实现后同标准绿灯均可复现。
4. 自身项目和建设任务可查；缺证据、缺任务和恢复查询结果正确，失败后状态保持。
5. 记录完整仍等待人工审核，FlowERP 未接入；学生没有将 V0.1 声称为完整自动交付系统。
6. 有本人首次判断、同伴／教师反馈、修订和第二次签字；未取得反馈如实标待复核。
7. 完成另一个项目的迁移设计，说明可复用能力与需重新确认的要求。

只交最终代码或绿色截图不能证明以上达成。提交字段见 [SUBMISSION](./SUBMISSION.md)。本讲评估设计理由与本人理解，同时保留大纲要求的最小实现证据。
