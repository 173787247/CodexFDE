# L01 教师备课说明

供教师备课使用，不属于学生讲义。学生正文先看最终成果，再以三问为主线：为什么需要个人工作台；怎样协同 Codex 改善交付质量；应该怎样设计。V0.1 实现放在设计之后，用于验证最小设计，不以操作命令串起课堂。

## 5. 30 分钟精讲怎样安排

线上讲解负责看懂流程和关键示范；完整实现与故障实验放在行动课。零基础学生可以暂停跟练，不要求在视频播放的 30 分钟内完成全部开发。

| 时间 | 课堂内容 | 学生当场动作 |
|---|---|---|
| 0～3 分钟 | 看工作台和 FlowERP 两个成果，说明各给谁使用 | 用自己的话说明两个成果的关系 |
| 3～9 分钟 | 第一问：交付责任、重复问题、工作台的价值与建设成本 | 写出问题—后果—能力对应关系 |
| 9～17 分钟 | 第二问：沿 V0.1 建设解释人与 Codex 分工，用重启后任务丢失、重复编号覆盖展示检查机制 | 标出输入输出与决定者，解释每项检查支持的结论 |
| 17～25 分钟 | 第三问：从工作流推导模块、对象、失败行为和最小范围 | 完成个人设计草图，说明 V0.1 取舍 |
| 25～30 分钟 | 说明课后怎样用 Spec、红绿对照和自举验证设计 | 指出已验证与待实现能力，明确课后产物 |

课后先完成个人设计，再按 [L01 行动卡](./行动卡.md)进行访谈、最小实现与验证。行动课可分段组织，时间由试讲数据调整；不把完整实现要求压入 30 分钟精讲，也不声称已验证学生完成时间。

## 演示与教学证据准备

> 课程建设状态说明：本讲教学目标、活动、产物与评价规则属于已经形成的课程设计；学生访谈记录、红灯、范围内 Diff、绿灯和自举证据属于待真实开课采集的学习证据。不得用参考仓库终态、Agent 自述或模拟学生记录替代本人达成。

讲师使用隔离工作区与练习数据，事先确认缺少本讲的 V0.1 能力。成品截图集中在开篇预览；后续演示使用同一项工作台建设任务。

讲师应回答：“任务创建后关闭程序还能查询吗？重复编号被拒绝后原内容还在吗？这些命令由谁运行、记录如何进入新工作台？”

**演示准备要求**：现成的工作台实现不能冒充本次建设；使用缺少目标能力的起点。展示真实 CLI 命令、首次失败、修复与重新查询。明确人组织执行，课程脚手架采集输出，学员实现的 V0.1 保存并查询记录。使用录制过程时注明时间与环境，并提供对应记录；未完成的演示如实标注待准备。

## 本次讲义的讲解要求

写作参考：[CS324 Introduction](https://stanford-cs324.github.io/winter2022/lectures/introduction/)、[Capabilities](https://stanford-cs324.github.io/winter2022/lectures/capabilities/)、[Data](https://stanford-cs324.github.io/winter2022/lectures/data/)，阅读日期 2026-09-05。参考其问题组织、概念与例子衔接、结果范围说明，不复用原课程内容，也不将此列为本课程教学成效证明。阅读正文承担论证，操作与提交要求集中在实践部分，减少反复跳转和标签打断。

面向受过高等教育、软件工程经验不同的学习者。降低先修知识要求，应通过补齐背景和因果关系实现：首次引入概念时说明它解决的具体问题，随后使用准确术语。避免用日常常识判断反复检查学生，也不要把术语数量、命令长度或记忆负担当成课程深度。

将课堂讨论集中到有取舍的问题：工作台的收益能否覆盖维护成本；测试是否经过真实功能；需求变化后如何解释旧结果；重复请求应该拒绝还是返回原结果。允许不同方案，要求说明前提、代价和可验证的方法。

实践指导区分三类困难：环境尚未满足、程序行为不符合预期、无法解释设计依据。分别补充操作支持、故障分析或推理讨论，不从终端熟练程度推断学生的理解能力。

全讲用“个人研发工作台”项目、“开发 V0.1”任务与前后两次运行贯穿：为什么需要查回依据，数据为什么分开，如何检查持久化与重复编号，以及怎样导入自己的建设记录。FlowERP 的业务例子集中在最终成果预览中，不承担 L01 的实现推导。

出版前仍需让目标学员试读：能否复述四个问题、能否解释第一版五个操作的必要性、能否从阅读自然进入实践。自动检查只能核对文件和课程合同，不能证明可读性已经达标。

## 分开检查“能运行”和“能解释”

| 现场表现 | 教师追问或动作 | 后续指导 |
|---|---|---|
| 命令运行失败 | 请学生指出期望结果，再看实际错误 | 能解释预期的，先解决环境或代码问题 |
| 命令运行成功，但无法解释记录归属 | 换一个任务编号，请学生预测查询结果及理由 | 回到项目—任务—运行记录关系图 |
| 可以解释编号，混淆需求版本 | 问“任务开始后需求文件改变了，应该按哪份验收？” | 回到快照例子，再实际查回保存内容 |
| 只展示最后一次通过 | 问“如何知道测试原先能发现能力缺失？” | 查看首次失败、同一测试和实际修订 |

以上追问先听预测，再观察操作。分别记录运行情况和解释情况，不以运行成功代替理解，也不因环境失败就判定概念未掌握。保留学生原回答与后续修订，不代写学生答案。

## 成果展示的主次

先展示个人工作台，说明这是首要建设成果，再展示 FlowERP，说明它是验证工作台价值、随持续开发而成长的伴生客户产品。讲解业务需求时，必须回到它检验了哪项工作台能力，以及产品结果暴露了什么需要改进的问题。
