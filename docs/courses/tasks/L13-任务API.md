# L13｜把执行链路封装成任务 API

> 机制与设计理由见对应讲义；本卡提供操作、允许修改范围和提交要求。提示词见 `docs/courses/labs/L13/prompts/`。

- **核心内容**：任务模型、异步执行边界、状态机、持久化和最小权限。
- **演示结果**：提交任务后获得 ID，并查询 Spec、执行阶段和最终结果。
- **课内增量**：实现任务提交与状态查询两个最小接口。
- **通过标准**：状态只按合法路径变化；失败原因可查询；已完成任务在服务重启后仍可读取。

## 本讲在“Codex → 个人工作台 → FlowERP”建设链中的位置

- **FlowERP 现场问题**：外部团队无法稳定提交和查询补货交付，并把 `202 Accepted` 错当成业务已经完成。
- **协作方式**：Codex 协助把工作台做成 Task API；提交者、执行者、审核者围绕同一 Task ID 协作，Codex 执行绑定合法状态和可追溯事件。

- **ERP 产品增量**：通过 Task API 提交并完成一项 FlowERP 补货需求，结果回指采购和库存对象。
- **工作台增量**：建立最小任务提交、状态查询、持久化和权限 API。
- **双线因果**：ERP 开始连续接收需求后，本地 Graph 无法被客户端稳定提交和追踪，迫使工作台形成可恢复 Task 资源。
- **ERP 验收证据**：补货 Task 回指 Spec、Eval、reviewer、采购单和库存结果；服务重启后同 Task ID 与业务对象仍能对账。
- **学生学习证据**：API 合同、状态码矩阵、竞态阻断和服务重启查询。
- **形成性评价**：学生先写资源语义再实现接口，`202` 被误写成完成需修订。

## 实践成果与核对要求

本讲不是给 CLI 套一个 HTTP 壳。学员必须亲手交付：Task 资源/状态/错误合同；提交与查询端点 Diff；持久化迁移；两个客户端并发领取和并发审核测试；幂等重放；非法迁移保持原状态；服务重启后同 ID/事件/失败可查；一个最小客户端或契约测试；迁移到第二资源的设计。

`202` 返回即写完成、并发靠内存布尔值、重启丢任务，或把单机线程宣传成分布式队列，均按未完成处理。

## 主次边界

- **FlowERP 产品状态**：必须由新 Task API 完成一项真实补货交付；不把工作台 Task API 混写成 ERP 领域 API；
- **工作台主产物**是通用 Task API、原子状态迁移、持久化、错误合同和最小权限；
- **迁移证明**要为第二类长任务定义资源身份、幂等键和冲突语义，不能复制 FlowERP 字段。

## 课前独立诊断

调用 AI 或实现 API 前提交且不得覆盖：

1. `202 Accepted`、`200 OK`、`409 Conflict` 分别能诚实说明什么？
2. 两个 Worker 同时领取或两个审核人同时决定，怎样保证只有一个成功？
3. 服务重启后最少要保留哪些 Task 事实？

## AI 使用与证据边界

- 先固定 API/状态合同再授权实现；AI 不得为了“成功”把非法迁移改成 200 或跳过人审；
- 写权限限制在 `workbench/` 与相关测试，数据库迁移、网络暴露和依赖安装需单独确认；
- 返回内容不得包含密钥、内部栈、任意本地路径或未经授权数据；错误应稳定且最小披露；
- Task 创建、Worker 领取、审核与事件写入必须通过持久化事实复验，前端计时器或模型叙述不算执行。

## 本讲主线

Graph 能恢复，但仍只能由本地命令驱动。学员把一次交付建模为有稳定 ID 的资源：创建返回 `202`，Worker 原子推进，客户端查询 Spec、阶段、Eval 和事件，并通过具名审核完成。本讲教授异步资源合同，不设计页面。

## 大纲与前沿硬校准

- **必须完成**：实现最小提交/查询接口，证明合法迁移、失败可查、并发冲突和重启后同 Task 可读。
- **当前做法**：资源身份、`202` 异步语义、幂等与条件更新是基础；webhook/callback 与 Outbox 属增强。
- **退回条件**：把 `202` 写成完成、把单机线程冒充队列、承诺未实现的多实例能力或提前设计 Web。见[课程蓝图](../课程蓝图.md)。

## 必须教会的知识

1. **资源而非 RPC 外壳**：Task 有身份、状态、版本、事件和链接；API 不只是“运行 CLI”的按钮。
2. **异步语义**：`202 Accepted` 表示已接收而非已完成；查询端点返回当前权威状态。
3. **原子迁移与竞争**：状态更新带前置状态；两个 Worker 或审核请求竞争时只有一个成功，冲突返回明确 409。
4. **持久 Worker**：创建、取任务、执行、写事件和重启恢复的边界清楚；当前单机线程不冒充分布式队列。
5. **错误合同**：校验错误、状态冲突、执行失败、未找到和未授权具有稳定状态码与机器字段。

## 留给下一讲

API 能说真话，但普通用户不会审读 JSON。L14 把真实状态投影成可核对的操作面板。


## 中断恢复：分清“检查中断”和“修改中断”

检查做到一半断电，可以保留失败现场后重新检查；代码改到一半断电，先确认改了哪些文件、是否还有进程在写，再决定下一次授权。

- 排队queued或合同已准备spec_ready：启动时继续调度，不把任务留在无人处理的状态。
- verify任务在executing/evaluating中断：先留下rework恢复事件，再重新复验；通过后仍停在review。
- codex任务在executing/evaluating中断：进入dead_letter等待人工核对；保留任务与事件，不自动重复改代码。dead_letter表示需人工处理，不表示证据被删除。
- 已经因阻断失败停在rework的任务：重启不能无限重复尝试，原失败原因保留。

维护者可运行 `python -X utf8 -m scripts.audit_task_recovery`：脚本在独立运行目录启动本地服务，暂停第一次复验，实际终止该子进程，再启动新进程完成真实课程Eval。输出保存终止前后任务、事件、进程日志与重启后幂等冲突证据。脚本只终止自己启动的进程；结果不代表学生本人实现，也不证明真实Codex代码交付或ERP新增功能。

学生需提交：终止前状态、原任务编号、重启后同编号查询、恢复事件、Eval、人审状态，以及为什么该任务能或不能自动重放。不能用“重新打开数据库”代替真实进程中断实验。

## 维护者复验补充（2026-09-05）：接口验收边界

必做 :8001 已提供 POST /api/v1/delivery/requests，要求 lesson、request、actor 和 Idempotency-Key；返回202、task_id、status_url与view_url。同键同内容不重复建任务，同键换内容返回409。后台只复验，绿后停在review；代码修改仍须课程CLI明确授权。单机线程不是分布式队列。独立Spec与提交键都可持久保留；HTTP测试已证明202先于Eval结束，服务进程强制中断恢复仍须另留证据。网页“提交并复验”现接入同一异步受理接口：受理后展示任务编号，检查期间自动读取状态，到人审或返工时停止；受理不等于检查通过。



### 关联真实业务编号，再核对状态

网页“开始一项交付”可展开“关联现有采购单或库存对象”，填写实际业务引用，例如 `PURCHASE:PUR-实际编号`。任务 API 的 `business_refs` 接受编号数组，保存到任务与交付视图；同一幂等键改用其他编号会冲突。引用只是提交者声明的对账线索，不会自动创建或审批采购单，也不能据此认定 ERP 交付完成。

练习先记录同一采购单的 API、业务服务和 SQLite 状态，再核对 DOM：未审批收货应拒绝，制单人自批应拒绝，另一位有权限的人审批后才允许收货过账；重放同一请求不重复增加库存。先写下你预计每步状态与数量，再记录实际差异。工作台任务审核与 ERP 采购审批分别进行，不用一个“通过”替代另一个。

参考实现已有真实 localhost HTTP 的采购审批、收货幂等和重新打开服务后的三方对账测试；测试使用隔离合成数据。它不替代学生的 DOM 走查、真实进程重启实验或本人实现前后的红绿证据。
