# L03｜把模糊需求变成可验收 Spec

> 机制与设计理由见对应讲义；本卡提供操作、允许修改范围和提交要求。提示词见 `docs/courses/labs/L03/prompts/`。

- **核心内容**：目标与非目标、正常与错误路径、边界条件、可执行验收项、最小变更原则。
- **演示结果**：把“增加导出功能”拆成结构化 `FDE_SPEC.md`。
- **课内增量**：由学生在外循环直接监督 Codex 实现 Spec 模板与最小解析器，只生成和校验合同结构，不执行 FlowERP 业务编码。
- **通过标准**：Spec 至少包含目标、非目标、约束、验收用例和来源；缺失必要字段时返回明确错误。
- **挑战任务**：从 Issue 或需求文档导入并保留来源追踪信息。

## 本讲在“Codex → 个人工作台 → FlowERP”建设链中的位置

- **FlowERP 现场问题**：运营、仓储和财务对“可用库存导出”给出不同口径，直接编码会得到多个互相冲突的正确答案。
- **协作方式**：Codex 是工作台共同建造者，协助实现 Spec Schema 与解析器；业务口径由具名人员签字，签字 Spec 才能成为 L04 的执行输入。

- **ERP 产品增量**：完成“库存导出”的具名产品决策与可验收合同；产品代码暂不变化。
- **工作台增量**：形成 Spec 模板、结构解析和来源追踪，不执行编码。
- **双线因果**：ERP 需求的对象、字段、权限和失败行为存在歧义，迫使工作台先形成机器可检、人能签字的 Spec 能力。
- **ERP 验收证据**：库存导出的字段、排序、空集、权限、写失败和失败后不变状态全部进入已签字 Spec。
- **学生学习证据**：Spec、正反用例矩阵、解析失败和跨组反向复述记录。
- **形成性评价**：机器评价结构，人和同伴评价语义；两类评价均通过才达成。

这里的“不执行编码”专指解析器不调用 Codex 实现 FlowERP 需求；学生仍须亲手实现并测试最小 Spec 结构解析器。L04 才消费签字 Spec 编写库存导出业务代码。

## 实践成果与核对要求

本讲不是写需求文档。学员必须亲手交付：价值判断；事实/推断/未知台账；导出需求歧义账与判别式追问；具名来源与决策记录；业务词典和八列 Schema；结构化 `FDE_SPEC.md`；最小解析器及缺失/空白/重复/错序/未知章节测试；正常、失败、边界、不变状态和变形关系矩阵；另一组只看 Spec 的盲验收与修订；迁移到第二需求的差异表。

只把 AI 初稿润色成完整文档、解析器只检查标题存在、安装一个 Spec 工具就宣称掌握，或另一组仍需作者口头解释，均按未完成处理。

## 主次边界

- **FlowERP 产品状态**：库存导出从模糊愿望晋级为已签字合同，L04 必须消费该合同完成实现；
- **工作台主产物**是可复用 Spec Schema、解析器、来源追踪与评审协议；
- **迁移证明**使用补货或个人项目需求，但不能取代大纲规定的导出基础案例。

## AI 使用与证据边界

- AI 可协助列问题、检查结构和生成反例，不得替业务责任人决定导出对象、权限、字段或口径；
- 本讲只读需求和实现 Spec 解析，不授权业务功能编码；若模型开始写实现应立即停止；
- 所有 AI 补充内容必须标记来源：原始需求、具名澄清、仓库事实或模型建议；模型建议不能伪装成已确认需求；
- 输入需求材料前先移除个人信息、客户数据、密钥和未经授权内容。

## 案例先行、工具后置

- 学生必须先从库存导出现场独立形成事实账、歧义账、业务词典、AC 和签署版 Spec；在此之前不得用工具参考产物覆盖初稿。
- **基础线**仍是 Codex 对话 + `FDE_SPEC.md` + `workbench/spec.py` + 具名 Review Record，不增加外部服务或 Node.js 依赖。
- Spec 签署后才介绍常用工具：用 Codex 直出作为无专门工作流的基线；用 Superpowers `brainstorming` 观察发现与批准门；用 OpenSpec proposal/specs/design/tasks 观察版本化变更。
- 外部工具由已有环境的小组或讲师演示；其他学员使用带版本和来源的冻结产物完成同题评审，不能把安装条件变成学习门槛。
- 工具评价统一使用本案例已经建立的标准：追问质量、假设治理、领域语义、验收辨识力、变更生命周期和人机责任。
- `writing-plans`、OpenSpec tasks 和 Codex 实施计划都属于 L04 交接，不能反向修改 L03 已签业务决定。
- Codex、Superpowers、OpenSpec 都不能替代需求来源、具名业务决定、语义评审和独立 Eval；工具安装截图不计学习证据。

## 本讲主线

运营只说“增加库存导出”，仓库、财务和开发却对导出对象、可用量口径、字段、排序、格式、权限和失败行为给出不同解释。学员必须把争议收敛为一份只允许一种产品口径的 `FDE_SPEC.md`。本讲产出合同，不写实现；缺货补货作为课后迁移案例。

### 写 Spec 前的需求判定卡（形成性证据）

对教师给出的第二条预设方案式输入，先完成以下卡片：

| 字段 | 要求 |
|---|---|
| 原始 Signal | 保留原话、来源和时间，不先改写成需求 |
| 用户问题 | 谁在什么场景试图完成什么，当前怎样做 |
| 当前证据 | 区分直接事实、间接迹象、推断和未知 |
| 非软件替代 | 至少一个流程、配置、人工或实验方案 |
| 决定 | Build / Experiment / Defer / Reject / Stop |
| 责任与复查 | 具名决定人，以及什么事实会推翻当前决定 |

只有 `Build` 进入完整 Spec；`Experiment` 只写假设、实验、指标和停止条件。该卡作为形成性学习证据，不替换大纲规定的库存导出 Spec 和解析失败基础通过线。

## 大纲与前沿硬校准

- **必须完成**：围绕“增加导出功能”生成并校验 Spec，保留来源、非目标、正反/边界用例与结构失败证据。
- **当前做法**：结构化输出只保证字段完整，人类通过跨组复述与反例签署业务语义。
- **退回条件**：开始写实现、让模型决定业务口径、用补货迁移案例替代大纲导出案例。见[课程蓝图](../课程蓝图.md)。

## 必须教会的知识

1. **七道决策门**：价值、事实、歧义、范围、行为、验收、签署必须依次关闭；不值得 Build 的输入不写完整 Spec。
2. **六段合同**：来源、目标、非目标、约束、验收用例、完成定义各自解决什么问题。
3. **事实分级**：仓库事实、具名决定、推断、未知和模型建议不得混写。
4. **结果而非实现**：验收描述八列 Schema、库存口径、顺序、错误与证据，不把函数名当需求。
5. **正反与变形用例**：Given-When-Then 同时覆盖正常、失败、空集、特殊字符、只读状态、顺序扰动和重复导出。
6. **结构/语义双门**：解析器拒绝缺失、空白、重复、错序和未知章节；人审用最小错误实现检验辨识力。
7. **版本与变更分层**：口径/Schema 改变升版 Spec；实现违约进入缺陷；Eval 抓不住错误则修裁判并保留旧失败。

## 课堂任务

先完成一张**外循环工作台建造工单 `WB-L03-SPEC`**。此时不能假装工作台会自动生成自己：学生在 L03 隔离起始工作区直接监督 Codex，只允许修改 `workbench/spec.py` 和对应测试，让解析器能够拒绝缺失、空白、重复、错序和未知章节。提交中必须保留给 Codex 的任务合同、实际 Diff、第一次失败、独立重跑结果以及学生拒绝的一条越界建议。解析器只判结构，具名人员仍负责业务语义。

```powershell
python -X utf8 -m workbench.cli course-contract --lesson 3
python -X utf8 -m workbench.cli course-spec --lesson 3
python -X utf8 -m workbench.cli spec .runtime/course/L03/FDE_SPEC.md
```

- 代码入口：`workbench/spec.py`；样例：`FDE_SPEC.md`。
- 正常路径：授权用户导出 `sku,name,site,location,lot_id,on_hand,reserved,available` 八列，`available = on_hand - reserved` 且按 SKU 升序。
- 边界路径：空库存仍输出完整表头；SKU/名称含逗号、双引号、换行或中文时可由标准 CSV 解析器逐字段还原；相同状态输出稳定。
- 失败路径：无权限、不支持的类型或写出失败返回明确错误；不泄露内容、不改变库存、不留下可误用半成品。
- 结构失败实验：至少复现缺失章节，以及重复/错序/未知章节之一，解析器必须指出具体原因。
- 语义失败实验：保持结构合法，却把 `available` 写成 `on_hand` 或把验收写成“实现函数”，由同伴用反例退回。
- 工具对照实验：同一句“增加库存导出功能”先不给、再给事实账与签署 Spec，比较 Codex 直出和一个 Superpowers/OpenSpec 路线；不得预设工具排名。

```powershell
python -X utf8 -m workbench.cli spec FDE_SPEC.md
```

## 独有产物与验收

提交 `WB-L03-SPEC` 的 Codex 原始委托、解析器 Diff 和红绿证据，以及七门决策记录、Spec、至少八场景用例矩阵、AC—证据映射、Review Record 和工具对照卡。另一组只看验收项，必须能一致还原导出对象、八列 Schema、可用量口径、排序、空集、转义、只读性和失败行为，并指出一个会被 AC 杀死的最小错误实现。工具对照卡必须引用真实或有来源的冻结产物，区分工具工作流、输入上下文和学生补充造成的差异；解析通过只证明结构完整，不等于业务语义正确。

## 提交证据包与四级量规

证据包包含课前价值/歧义判断、事实/推断/未知台账、需求来源、判别式追问、业务词典、Spec 初稿、两类解析红灯、语义反例、AC—证据映射、具名决策、跨组复述、修订稿、AI 采纳/拒绝记录、同题两轮工具产物、工具覆盖/缺口卡和迁移 Spec。

| 维度 | 优秀 | 达成 | 发展中 | 未达成 |
|---|---|---|---|---|
| 判断与来源 | Build 决定可反驳，事实/推断/未知与拒绝建议全可追溯 | 来源、决定人和未知项明确 | 有来源但把推断写成事实 | 虚构来源或工具代签 |
| 范围与业务合同 | 目标、非目标、八列 Schema、口径与约束互相一致且不绑无关实现 | 六段必要内容完整且口径唯一 | 有字段但边界或消费者含糊 | 缺必要章节或多种相反实现都合法 |
| 验收辨识力 | 正反、边界、不变状态和变形关系能杀死共享错误假设 | AC 可执行且有权威证据 | 只有 happy path 或只检查错误消息 | 用实现步骤冒充验收 |
| 学生修订与工具判断 | 能区分合同/实现/Eval 缺陷，用案例证据评价工具并实质升版 | 至少一项有证据修订、具名签署和工具缺口判断 | 只让解析器变绿或只复述工具功能 | 直接提交 AI/工具生成产物或无证据排名 |

硬门槛：编造需求来源、让 AI 代替业务签字、解析通过即宣称可验收，或在本讲越权编码，直接退回。
