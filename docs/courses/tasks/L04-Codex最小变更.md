# L04｜委托 Codex 执行一次最小变更

> 机制与设计理由见对应讲义；本卡提供操作、允许修改范围和提交要求。提示词见 `docs/courses/labs/L04/prompts/`。

- **核心内容**：非交互执行、工作目录、权限边界、结果采集与人工确认点。
- **演示结果**：读取第 3 讲 Spec，委托 Codex 完成一个小型代码变更并运行测试。
- **课内增量**：先由学生直接监督 Codex 补齐并独立验收 Workbench V0 的执行入口、写集检查、最小 Eval 和结果摘要，再由 V0 在授权工作区调用 Codex 交付库存导出；不额外包装为文件读写 MCP。
- **通过标准**：变更能够运行；基础测试通过；摘要包含修改文件、验证命令和剩余风险；密钥和环境文件未提交。

## VS Code 行动入口

1. 阅读对应讲义的问题与机制部分，记录自己的初始判断和待确认问题，再进入实践。
2. 打开 [FlowERP-AI研发工作台.code-workspace](../FlowERP-AI研发工作台.code-workspace)，运行“课程/02 查看本讲合同”，讲次选择 `4`。
3. 回到本卡确认允许写集、失败语义和独有产物；再执行本讲命令，不用最终仓库绿灯替代个人红→绿过程。
4. 将失败、Diff、复验和权威状态写回 Markdown 提交包，完成第二次签字。

> 讲义负责案例、机制和第一次判断；本卡负责实验动作；VS Code 负责执行。三者之间的交接物是签字版合同、允许写集、失败语义和复验证据。

## 本讲在“Codex → 个人工作台 → FlowERP”建设链中的位置

- **FlowERP 现场问题**：库存导出合同已经签字，但宽泛委托会诱发无关重构、越界写入和执行者自证成功。
- **协作方式**：本讲是自举换挡点：学生先监督 Codex 补齐 Workbench V0，再通过 V0 组织授权、执行、独立复验和人审，协同交付库存导出。

- **ERP 产品增量**：由工作台实现并验收库存导出，覆盖正常、空集和写失败路径。
- **工作台增量**：形成 Codex 执行入口、基线派生的隔离 Worktree、写集边界、执行前后 Eval 和结果摘要，完成 Workbench V0。
- **双线因果**：首个 ERP 实现暴露宽泛委托的越界风险，迫使工作台建立能力信封；升级后的工作台必须真正交付库存导出。
- **ERP 验收证据**：库存导出真实 Diff；正常、空集和写失败用例；非执行者用同一 Spec 独立签收。
- **学生学习证据**：能力信封、真实 Diff、边界测试、独立复验和风险摘要。
- **形成性评价**：执行者不能给自己判定成功，由同伴按文件级因果关系复核。

## 实践成果与核对要求

本讲不是观看 Codex 写代码。学员必须亲手交付：由 L03 验收项反推的读/写/禁止集；一次只计划不写入的越界预测；一次受控真实执行；白名单外写入阻断证据；空集/特殊字符/写失败测试；逐文件 Diff 因果审查；非执行者独立复验和剩余风险摘要。

直接运行宽泛 Prompt、用模型自述代替复验、或把无关重构包装成“顺手优化”，均按未完成处理。

## 主次边界

- **FlowERP 产品状态**：必须完成 L03 库存导出，不扩展到无关采购或 Web；这是一项真实产品增量而非演示夹具；
- **工作台主产物**是能力信封、受控执行入口、写集约束、结果采集和独立复验协议；
- **迁移证明**要求在第二个小型 Spec 上先设计授权，不能靠复用同一 Prompt 证明可迁移。

## 课前独立诊断

在运行 Codex 前提交且不得覆盖：

1. 从 L03 Spec 推导预计读集、写集、禁止集和人工确认点。
2. “改动文件少”为什么仍不一定是最小闭环？
3. 哪些证据必须由非执行者独立取得？

## 混合式学习流程

## AI 使用与证据边界

- 写入只允许发生在隔离工作区和显式白名单内；网络、依赖安装、提交、推送及敏感文件默认禁止；
- 委托采用目标、上下文、允许、禁止、输出证据、完成/停止六段式，并记录工具、模型可见信息、提交和实际命令；
- 模型声称测试通过不计证据，委托者必须重跑并保存退出码；
- 任何写集扩张、未知脚本、密钥请求或不可逆动作都必须停止并重新授权。

## 本讲主线

L03 的库存可用量导出 Spec 固定后，本讲分成两个有先后关系的 Ticket。`WB-L04-BOOTSTRAP` 由学生直接监督 Codex 补齐 Workbench V0 的执行模式、写集检查、前后快照、最小 Eval 和摘要；它通过独立测试后，`REQ-COURSE-L04` 才允许调用新入口交付库存导出。学员必须分别解释工作台 Diff 和 ERP Diff 的因果，不能用同一次模型运行让执行器给自己验收。低库存标记只作为课后同构迁移，不扩建通用 Agent 平台。

## 大纲与前沿硬校准

- **必须完成**：消费 L03 Spec，形成执行入口、受控 Diff、独立复验和包含修改文件/命令/风险的摘要。
- **当前做法**：显式工作目录、写入白名单、最小权限是基础；JSONL 与输出 Schema 是可替换增强。
- **退回条件**：扩建通用 Agent 平台、用 MCP 包装基本文件操作、顺手重构或让执行者给自己判成功。见[课程蓝图](../课程蓝图.md)。

## 必须教会的知识

1. **能力信封**：请求、写入范围、超时、执行模式和验证命令共同构成授权，Prompt 不是全部权限。
2. **最小变更半径**：从验收项反推最少模块、接口和测试，不“顺手重构”。
3. **边界测试**：空集、稳定顺序、特殊字符和写入失败比单一 happy path 更能约束导出语义。
4. **Diff 审查**：逐文件核对范围、因果关系、兼容性、秘密和生成产物。
5. **独立复验**：模型自述与其运行日志都不能替代委托者重跑命令。

## 课堂任务

### Ticket A｜直接监督 Codex 完成 Workbench V0 自举

- 输入：L02 规则、L03 签字 Spec、`WB-L04-BOOTSTRAP` 能力合同；此时不得调用尚未被证明的 `course-submit --execute-code` 给自己背书。
- 允许写集：执行入口、任务执行模式/写集校验、前后快照与摘要所需的 `workbench/` 最小文件和对应测试；禁止修改 `flowerp/`。
- 必须先红：只验证模式不得写文件；改代码模式缺少写集必须拒绝；白名单外写入必须被识别；退出码、Diff 和最小 Eval 必须进入证据。
- 验收：非执行者重跑工作台测试并审查 Codex Diff；只有 Ticket A 被具名接受，才进入 Ticket B。

### Ticket B｜通过 Workbench V0 授权 Codex 交付 FlowERP

```powershell
python -X utf8 -m workbench.cli course-contract --lesson 4
python -X utf8 -m workbench.cli course-spec --lesson 4
python -X utf8 -m workbench.cli course-submit --lesson 4 --execute-code --bootstrap-task-id TASK-替换为实际编号 --actor "构建学生姓名" --execution-timeout 900
python -X utf8 -m workbench.cli course-eval --lesson 4
```

- 正常路径：只修改导出所需领域代码和相应测试，字段、可用量与稳定顺序符合 Spec。
- 边界路径：空集、特殊字符和写入失败至少三类断言通过，失败不留半成品。
- 失败路径：要求同时重命名库存模型、改 Web 配色或修改白名单外文件，执行应拒绝或评审退回。
- 不变状态：预占、幂等入库、采购审批行为不变；运行数据库和报告不入库。

## 独有产物与验收

提交两个互相回指但不可合并的证据包：Ticket A 保存工作台能力合同、Codex 原始轨迹、工作台 Diff、三类边界红灯和独立签收；Ticket B 保存基线标签、隔离 Worktree 身份、ERP 写集、执行前红灯、库存导出 Diff、执行后绿灯、命令/退出码/Token 记录和剩余风险。任何白名单外写入、基线预先为绿、零改动、无关重构、工作台自证自己正确，或“Codex 说测试通过但未独立重跑”均退回。

## 提交证据包与四级量规

证据包包含课前授权判断、六段式委托、权限配置、AI 原始轨迹、Diff、边界红绿证据、非执行者复验、修订说明、交付摘要和迁移能力信封。

| 维度 | 优秀 | 达成 | 发展中 | 未达成 |
|---|---|---|---|---|
| 授权控制 | 能力信封可机器约束且遇扩范围会停止 | 读写/禁止集和停止条件明确 | 只在提示词中约束 | 越权写入、联网或读取敏感数据 |
| 最小闭环 | 每个文件都可回指验收项且无因果污染 | 变更范围合理、功能完整 | 少量无关改动或解释不足 | 大规模顺手重构、跳过 Spec |
| 验证证据 | 边界、失败和独立复验齐全 | 基础测试和关键边界通过 | 只有模型日志或单一 happy path | 未运行却写通过、删除失败证据 |
| 学生审查 | 能发现 AI 初稿问题并实质修订 | 至少一项有证据修订 | 只改摘要文字 | AI 自审自签收 |

硬门槛：白名单外写入、秘密/环境文件进入提交、未经授权推送、未独立复验却宣称完成，直接退回。

## 持续改进与迁移

记录越界率、无关改动率、边界漏测率、独立复验完成率和首次/修订量规变化；Token 数据不可核验时写“未知”。迁移必须重新推导能力信封，不能沿用本讲文件白名单。

## 留给下一讲

现有测试可能与实现共享同一个错误假设。L05 从已知缺陷出发，验证裁判真的会判错。


### 起始失败要落到产品能力

若起始检查只提示课程能力未启用，先由工作台核对隔离准备，不要让Codex越界修改课程门槛。历史基线的库存导出可能位于通用导出服务，不能只按新版文件位置判断。去掉课程辅助门槛后若检查已经通过，仍不能作为本次实现起点；应准备实际缺少库存导出能力的隔离副本。实现后还要打开导出文件，核对现存、预占和可用数量；单个红绿结果不替代本讲两张Ticket及独立验收要求。

### 从独立验收到任务交接

Ticket B 必须用 `--bootstrap-task-id` 引用已接受的 Ticket A；网页在授权前填写同一编号。构建者创建 Ticket A，非构建者亲自复验并决定签收，系统保存两张任务的双向引用。具体操作见[工作台独立验收衔接](../../reference/L04工作台独立验收衔接.md)。这是职责记录检查，不能替代原始红绿证据和课堂答辩。

### 追加反证：已验收的代码被改过

在隔离练习中，对工作台验收覆盖的源码作一次小修改，再尝试沿用旧 Ticket A。预期在签收或 L04 启动前被拒绝，不启动 Codex。提交首次判断、修改文件、拒绝结果和重新独立复验后的修订说明。源码指纹随报告保存，范围与操作见[验收衔接说明](../../reference/L04工作台独立验收衔接.md)。它核对磁盘源码，不证明人员身份或冻结运行环境。

## 课堂判断：两张任务单不能混为一次通过

先用维修工单类比说明允许修改与停止条件，再分别画出任务 A（工作台独立验收）与任务 B（库存导出交付）。学员先判断“导出做好了，但订单取消逻辑也被顺手修改”是否可以接受，然后说明对应的范围与改动证据。代码短例只验证路径检查：业务文件可进入清单，`.env` 被拒绝；它不启动 Codex，也不代表任务已经授权。提交初次判断、同伴反证和修订理由，并回到两张真实任务单核对 ERP 增量、工作台能力及独立验收记录。
