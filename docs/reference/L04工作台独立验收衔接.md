# L04：让独立验收的工作台接手 ERP 任务

本页解决一个操作问题：如何把已经独立接受的工作台 Ticket A，交给库存导出 Ticket B 使用。

## 先完成建设，再登记独立复验

学生直接监督 Codex 完成工作台 V0，并保留本次能力合同、实现前失败、修改文件、实现后结果及原始执行轨迹。此时不调用尚未验收的 `course-submit --execute-code` 自证。

随后由构建学生创建一条复验记录。以下命令中的姓名和 Spec 路径必须换成实际值；Spec 是已经签署的工作台能力合同，不能拿 ERP 导出合同代替。两人使用同一个运行目录。

```powershell
.venv/Scripts/python.exe -X utf8 -m workbench.cli task-create --runtime-dir .runtime --requirement-id WB-L04-BOOTSTRAP --request "独立验收本次 Workbench V0；证据位置见签署 Spec" --spec-path "docs/courses/labs/L04/WB-L04-BOOTSTRAP.md" --actor "构建学生姓名"
```

上面的 Spec 文件需要学生根据 L03 规则实际编写；命令返回的 `TASK-…` 是 Ticket A 编号。此记录采用仅复验模式，不会让尚未证明的工作台再执行一次代码建设。

由未参与构建的同伴打开原始证据、审查 Diff，并亲自重跑工作台边界测试：仅复验不改代码、缺少写集拒绝执行、越界改动被识别，以及退出码和报告可追溯。统一 Eval 不能替代这些针对本次改动的断言。

```powershell
.venv/Scripts/python.exe -X utf8 -m workbench.cli task-run TASK-替换为实际编号 --runtime-dir .runtime --actor "独立复验同伴姓名"
.venv/Scripts/python.exe -X utf8 -m workbench.cli task-show TASK-替换为实际编号 --runtime-dir .runtime
```

最后由同伴本人决定是否接受，并在理由中注明亲自查看的证据和仍有的风险。未通过则选择 reject，不要复制下面的 approve 作为默认答案。

```powershell
.venv/Scripts/python.exe -X utf8 -m workbench.cli task-review TASK-替换为实际编号 --runtime-dir .runtime --reviewer "独立复验同伴姓名" --decision approve --note "填写实际复验命令、Diff 审查结论和剩余风险"
```

独立复验者可以同时签收；构建者不能给自己签收。记录里的署名用于追责，不提供身份认证，也不能证明两个人实际独立完成了工作。教师仍须抽查原始证据和现场解释。

## 再交付库存导出

```powershell
.venv/Scripts/python.exe -X utf8 -m workbench.cli course-submit --lesson 4 --execute-code --bootstrap-task-id TASK-替换为实际编号 --actor "构建学生姓名" --runtime-dir .runtime --execution-timeout 900
```

网页启用代码执行时，在“L04：已接受的工作台任务编号”填写同一编号。授权预览会展示前置任务、独立复验人与接受人；确认后才启动本次隔离执行。

如果编号不存在、引用其他需求、Ticket A 未完成、由构建者自签或最近复验仍由构建者运行，系统拒绝启动。成功创建后，两张任务的事件记录互相引用。Ticket B 仍须经历库存导出的真实起始失败、范围内改动、独立复验和人工验收，不会继承 Ticket A 的通过结论。

## 这道检查证明什么

它检查的是同一运行库中的职责记录和先后关系。它不替代工作台代码审查、原始红绿证据或学生迁移答辩，系统在独立复验前后、签收时和 L04 启动前，核对本地控制源码指纹。指纹覆盖 `workbench/`、`eval/`、`agent/`、`tests/`、`.codex/` 中列明类型的源码与配置，以及根目录 `AGENTS.md`、`FDE_SPEC.md`、`pyproject.toml`、`main.py`；完整文件清单随复验报告保存。新增、删除、修改覆盖文件，或换工作区，均须重新独立复验。没有指纹的旧 Ticket A 不能继续用于新执行。


## 课堂故障实验：旧的验收还能用吗？

先写下判断：同伴签收后，构建者又“只改了一行”执行入口，原来的通过结论是否还有效？

在个人隔离练习目录完成 Ticket A 的复验后，先保存修改前副本，再改一处覆盖范围内的工作台代码。尝试签收或创建 L04 执行方案，应看到“工作台源码已变化”，且 Codex 尚未被启动。记录变更文件、拒绝原因与自己的首次判断；修订后重新独立复验，再由同伴本人决定签收。不要用直接恢复数据库中的摘要绕过检查。

思考迁移：为什么输出报告不应每次改变源码指纹？为什么换工作区后，即使文件名相同，也不能只凭原任务编号接受？

边界说明：指纹检查绑定的是本地磁盘文件，不是人员身份、Python 依赖环境或已加载进程的内存代码；它也不冻结后续并发编辑。工作台进程在源码修改后应重启，课堂执行期间不要并行修改这套控制代码。严格的发布版本和运行环境认证仍是后续建设项。
